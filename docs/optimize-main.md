# LieUI `main` 优化方案（v2 · 评审修订版）

> 分支：`main`（lieui v3 Retained MVP，纯 CPU 渲染）
> 基线：`docs/architecture-v3.md`（v3.4-draft）、`docs/operation-log.md`（实测记录）
> 状态：**v2 已评审修订**（v1 的 A/B 两条前提有误，已否决并重定向）
> 约束：不违反 v3 简化哲学（无用户 Widget 树、无 `Msg`、R1 响应式、`Kind` 枚举分派、事件驱动）

---

## 〇、v1 → v2 修订说明（评审结论）

v1 提出两条优化，经对照既有设计与实测记录复核，**两条前提均不成立**，故否决并重定向。

### 0.1 否决清单

| v1 主张 | 处置 | 依据 |
|---|---|---|
| A：`KindDesc` 瘦身为 5 原语、控件退化为组合函数 | **否决** | 摧毁框架内置行为的**分派键**；且"枚举成员多"不是复杂度度量 |
| B-1：当前是 `damage_batches_bands` 行带、太粗要删 | **前提错误** | 默认走 `damage_batches`（精确碎片矩形），band 已被明文否决 |
| B-2：上 compositor 就不用脏区、直接替代 | **否决** | 两者**正交**；合成器以脏区为输入 |
| B-3：每叶子建 pixmap + atlas/LRU | **降级 + 改粒度** | 省的是光栅化，而实测瓶颈在场景重建；粒度应为子树 |
| B-4：`dirty: bool` 替代脏矩形 | **否决** | 丢失旧 bounds ⇒ 必然复现残影 |

### 0.2 四条事实性纠正

1. **默认脏区策略不是 band**。
   `src/render/raster.rs:398` 默认 `damage_batches`（每矩形单独渲染进复用 `scratch`）；
   `damage_batches_bands` / `damage_batches_union` 只是并列的可选策略。
   `architecture-v3.md:688` 早已**明文否决行带**：*"不要用'全宽行带'……会把 38×77 的文本脏区放大成 400×77（收益减半）"*。
   ⇒ "band 太粗"是对**已修复问题**的重复诊断。

2. **compositor 优先级已被实测下调**。
   `operation-log.md:5549-5670`：20000 行时 layout 占 94% ⇒ 初判"compositor 值得做"；
   但真凶是测量缓存"超限整表清空"，修掉后 **47.0 → 11.0 ms（4.3x）**，
   结论 `:5665`：**"compositor 的优先级下降"**，新优先级为 ① 部分布局 → ② 增量场景 → ③ compositor。

3. **compositor 与脏区正交，不是替代**。
   `operation-log.md:1412-1422`：合成器回答"怎么叠"，脏区回答"这次要重算哪里"；
   *"现代合成器一律以脏区为单位增量合成"*（Wayland `surface.damage` / Win32 update region / macOS `setNeedsDisplayInRect`）。

4. **"枚举成员个数"不是复杂度度量**。
   `architecture-v3.md:981`：*"简化的度量是'机制个数'，不是'枚举成员个数'"*（该原则正是为 `EventKind` 17→40 而写）。

## 一、修正后的诊断

### 1.1 真正的瓶颈（实测，非推测）

`operation-log.md:1395-1399`：

> 1. **脏区把光栅化从 ms 拉回 µs**（整窗占 60fps 预算的 **15~43%**），空闲帧几乎为零——"有脏才画"确实成立，**不该退化**。
> 2. **局部重绘耗时随节点数线性增长**（49µs → 388µs）：瓶颈已不在光栅化，而在**每帧全量重建场景 + 剔除（O(N)）**。下一步该做的是**增量场景 / 保留 draw list**。

`operation-log.md:5672-5678`：

> `build()` 递归遍历**整棵子树**，给**不可见**的节点也设 `measure_text`。这才是根本浪费——可见的只有 40 行，却为 25000 个节点做了准备。
> ⇒ **"只布局可见部分"比"缓存布局结果"更本质**。

⇒ **一号瓶颈在布局侧与场景侧，不在光栅侧。** v1 优化的是非瓶颈层。

### 1.2 真正的痛点

脏区的成本**不在 rect 数学**，而在"**登记必须完备**"这一固有义务：
漏标 ⇒ 残影（`operation-log.md:1401-1410` 有真实案例：换主题漏标整窗、`CustomNode` 自绘漏 `cx.damage`）。
这是**任何**增量方案的代价；整窗重绘只是把它换成"每次 2.5~7ms"。

真正的**可简化靶子**是 `damage_batches` 的批处理启发式（取整/裁剪/去重/近邻合并/碎片>8/面积>45% 退化整窗）——
在 O(N) 场景重建主导下，其边际收益已很小。

## 二、优化计划（按日志既定优先级）

| # | 内容 | 收益依据 | 风险 |
|---|---|---|---|
| **P1** | **部分布局**：`build()` 按 dirty 范围裁剪子树，只为可见/受影响子树设 `measure_text` | `:5672-5678` "只布局可见部分……更本质" | 中（需与重排边界机制对齐） |
| **P2** | **增量场景 / 保留 draw list**：`SceneBuilder` 不再每帧全量重建 | `:1397-1399` 已点名的下一步 | 中高（失效判定） |
| **P3** | **`NodeFlags::CACHE_AS_BITMAP`**（子树级栅格缓存） | `:964-965` 已留位 | 中（失效/内存） |
| **P4** | **脏区登记入口收敛**：把散落的登记点收拢，降低漏标概率 | `:1401-1410` 真实 bug 类 | 低（纯重构） |

**P1 → P2 → P3 严格有序**（compositor 类优化在 P2 之后收益才明显）。

### 2.1 明确不做

- ❌ `Kind` 枚举 DOM 化（见 §三）
- ❌ 用节点 `dirty: bool` 替代脏矩形（丢旧 bounds ⇒ 残影）
- ❌ 每叶子 pixmap + tile atlas（省非瓶颈层 + 内存复杂度）
- ❌ 取消脏区改整窗重绘（实测 2.5~7.2ms/次；hover/滚动/动画/4K 下持续 15~43%）
  > 注：整窗重绘需求**今天就有逃生舱** `WindowConfig::full_repaint(true)`（`:1428-1430`），无需拆脏区。

## 三、关于 `Kind` 枚举的结论：不 DOM 化

### 3.1 `Kind` 不是 widget 扩展点

`Kind` 装的是**框架自有控件**（`:269`：*"框架拥有 measure/draw/behavior 的完整实现"*）。用户扩展走既有三档（`:828-836`）：
A 组合 = **普通函数**（零机制）/ B 自绘 + C 自定义行为 = `Kind::Custom`。

"往 `Kind` 加变体麻烦"——**这件事本就不该常发生**。WinUI 同形状：`Button`/`Slider` 是框架密封类，用户不去"给 UIElement 加成员"，而是子类化 `Control`/`UserControl`（`:911-912` 已作此对照）。

### 3.2 DOM 化三种形态的代价

| 形态 | 代表 | 保留 enum 收益 | 风险 |
|---|---|---|---|
| ① enum + 每变体 typed struct | refactor `DomNode::Text(TextNode{..})` | ✅ 仍可 match / derive Eq | 低，但**不解决痛点**（加控件仍要加变体） |
| ② 每节点 `Box<dyn Node>` | 真 DOM / Web-like | ❌ 两者皆失 | **高**，见下 |
| ③ 用户 `Widget` trait + `build()` | 重引 Widget 树 | ❌ | 违反 v3，已否决 |

形态 ② 会撞的五个问题：

1. **借用冲突**（`:290-294` 明文关键决策）：trait 对象下"可变借用节点自身"与"把 `&mut Track` 传给组件行为"必然冲突；现有自由函数 `fn slider_handle(track, id, ev, cmd)` 借用天然可分。
2. **丢 `derive(PartialEq)`** ⇒ 被迫重引 `tree_eq`/downcast。**downcast 已试过并被放弃**（`:885-889`：*"放弃 `update_desc(&dyn Any)` downcast 协议"*，改用 `CustomCell` 指针判等）。
3. **性能**：25000 节点下每节点堆分配 + 虚调用；现 `Kind` 内联且 `Track`/`Node` 全非泛型（`:822`）。
4. **丢编译期穷尽性**：`match` 逼你改完所有分发点——这份"麻烦"**正是买来的安全**。
5. **`Kind::Custom` 能持有 trait 对象，是因为它的 hook 不拿 `&mut Track`**（`:894-898`）。该豁免只对逃生舱成立，不能推广到必须直接操作保留树的框架自有组件（`:598-603`）。

### 3.3 正确的扩展口子

要开"第三方一等公民控件"，走设计已预留的 **`WidgetKindRegistry`**（`KindId` + 行为函数表，`:905-906`），不动核心。**不 DOM 化。**

## 四、关于 compositor / 脏区的结论

### 4.1 "Widget 声明自己 dirty" 就是脏区，且 `main` 已实现

- `cmd.damage(id)`（自绘组件自标脏，`:888`）
- `cx.damage(key)`（用户态只重绘、不重跑 `view()`，`:438`）
- patch 时刻 `Track::damage_bounds(id)` 沿祖先链组合变换抓矩形（`src/track.rs:1143-1145`：*"必须在节点还活着时问 `damage_bounds`"*）

即：**变更发生的那一刻捕获矩形（含旧 bounds）**。"声明 dirty"决定**谁要重画**，矩形决定**屏幕哪块要重画**。缺后者即残影。

### 4.2 "有变化就整窗重绘"的实测成本

一次整窗光栅 ≈ **2.5~7.2ms**（`:1395`：整窗占 60fps 预算 15~43%）。

| 场景 | 频率 | 整窗代价 |
|---|---|---|
| 点按钮 / 敲字 | 低频 | ✅ 可接受 |
| hover 反馈 | 每次 mousemove（60~120/s） | ❌ 持续 15~43% |
| 滚动 | 每 wheel/tick | ❌ 同上（日志反复测 20000 行） |
| 动画 / spinner | 60/s | ❌ 吃满预算 |
| 4K 大窗 | ×8 像素 | ❌ 20~56ms/次 |

⇒ 整窗重绘**仅在静态小窗成立**；hover 是任何 GUI 都有的，故 `:1396` 结论"不该退化"。

### 4.3 per-widget pixmap 治不了当前瓶颈

它省的是**光栅化**，而实测瓶颈是**场景重建 + 剔除的 O(N)**（`:1397-1399`）。
且缓存**不减少遍历**——仍要走完整棵树才知道"该 blit 哪些缓存"，除非再加空间索引（新复杂度）。
故应排在 P2 之后。

## 五、验收标准

| 项 | 指标 | 当前基线 |
|---|---|---|
| P1 部分布局 | 20000 行滚动布局耗时 | 11.0ms（`:5661`） |
| P2 增量场景 | 局部重绘随节点数的增长斜率 | 49µs → 388µs（O(N)，`:1397`） |
| P4 登记收敛 | 漏标类 bug 数 | 见 `:1401-1410` 案例清单 |

通用门禁：`cargo test --workspace` 全绿、`cargo clippy --workspace --all-targets -D warnings` exit 0、`cargo fmt --all --check` 0 差异。
性能结论须**逐点复现**（`:5641-5648`：已两次栽在污染数据上，*"任何'复杂度变化'的结论，必须逐点复现"*）。

## 六、与 v3 哲学的一致性

- ✅ 保留 `Kind` 枚举分派 + `Kind::Custom` 逃生舱（不引入 Widget 树 / `reconciler` / `Msg`）
- ✅ R1 响应式回路不变：`Signal` 变更 → 标脏 → 重跑 `view()` → 对齐
- ✅ 脏区保留（声明 + 变更时刻抓 bounds），仅收敛登记入口
- ✅ 事件驱动 + 空闲零功耗不变
- ✅ 优化目标对齐实测瓶颈（布局侧 / 场景侧），而非光栅侧
